# UI/UX Design System Guidelines

**Purpose:** keep the frontend visually and structurally consistent when different AI agent sessions (or humans) touch the UI independently, without re-deriving decisions each time. Read this before redesigning or adding to any page in `04_frontend/`.

---

## 0. Stack decision (don't relitigate this)

The frontend stays **vanilla HTML5 + CSS3 + JS (ES6+), no framework** — confirmed as-built per [[07_document/AI_Agent_Entry]]. A Next.js/Tailwind/shadcn migration was proposed once and explicitly deferred: finish redesigning all pages in the current stack first; only reconsider a framework migration afterward, and only if there's a concrete feature need (not aesthetics alone — the same design system below achieves the "clean enterprise SaaS" look without a framework change). Do not start a framework migration as a side effect of a styling task.

## 1. Where things live

- **Shared, reusable rules** → `04_frontend/css/style.css`. This is the single site-wide stylesheet loaded by every page — CSS custom properties (`--bg-card`, `--highlight`, `--accent`, `--border`, `--text-primary`, `--text-muted`, `--danger`, etc.), theme (`.dark-mode` on `<body>`, toggled by `ThemeManager` in `js/app.js`), and now the shared component classes listed below.
- **Page-specific rules** → a `<style>` block in that page's own `<head>`, placed after the `<link rel="stylesheet" href="/css/style.css">` tag so it can override by source order. Only put something here if it's truly specific to that page (e.g. `.auth-tabs` segmented control only used on `login.html`).
- **Never invent a new color palette.** Reuse the existing `var(--*)` tokens so every page still respects both light and dark mode. Check both modes before considering a color "done" — several of the tokens' light/dark values are not simple opacity variants of each other (e.g. `--danger` is `#fa5252` in light, `#e74c3c` in dark; `--highlight` is `#fa5252`/`#e94560`) so a hardcoded `rgba(...)` picked from one mode will look wrong in the other. Pair overrides explicitly:
  ```css
  .thing { background: rgba(250, 82, 82, 0.06); }       /* light */
  .dark-mode .thing { background: rgba(231, 76, 60, 0.06); } /* dark */
  ```

## 2. No emoji, ever, in UI chrome

Emoji (💻 ☰ 🔒 🛒 🌙 etc.) read as "AI slop" and were the main complaint that started this redesign. Replace them with inline SVG icons, lucide-style convention:

```html
<svg class="icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" aria-hidden="true">
  <!-- simple line/rect/circle primitives only — see below -->
</svg>
```

- Always `stroke="currentColor"`, never a hardcoded hex — this lets the shared `.icon { color: ... }` rules (and parent-scoped color overrides like `.navbar-logo .icon`) theme the icon automatically.
- Size via the shared `.icon` class (18×18 default; `.navbar-logo .icon` / `.mobile-menu-toggle .icon` are 22×22 — both defined once in `style.css`, don't redefine per page).
- **Only hand-type path data you're confident in.** Simple icons (rects, straight lines, circles — menu, monitor, mail, lock, user) are safe to author directly. For icons with multiple Bézier control points (phone, complex glyphs), copy exact path data from lucide.dev rather than recalling it from memory — a single wrong coordinate silently renders a blank/malformed icon with no console error. Always screenshot-verify new icons (see §5).
- Exception: **brand marks stay as-is** — the Google/Facebook SVG logos in the social-login buttons are brand assets, not UI icons; don't reduce them to monochrome or apply `.icon`.
- Exception: plain typographic arrows (`→`, `←`) used as text-only affordances (e.g. "ดูสินค้าทั้งหมด →" link labels, `<option>` text inside a `<select>`) are NOT emoji and don't need SVG replacement — `<option>` can't contain markup anyway. Only replace an arrow if it's standing in for an icon in a context that could hold one (a button, a heading).
- **Dynamic content generated by separate `.js` files is just as in-scope as static HTML.** `js/app.js` (global cart modal, checkout flow, navbar cart/auth links, theme toggle) and `js/builder.js` (category icons, compatibility status rows, cross-match panel) both had substantial emoji embedded in template-literal strings that were easy to miss by reading only the `.html` file — always grep the actual `.js` files a page loads, not just its own markup, before declaring a page done.

## 3. Shared component classes (already in `style.css` — reuse, don't redefine)

| Class | Use |
|---|---|
| `.icon` | any inline SVG icon (18×18 default) |
| `.form-input-group` | wraps a `.form-input` + a leading `.icon` (absolutely positioned at `left: 0.85rem`, input gets `padding-left: 2.6rem`) |
| `.form-input.has-error` | red border + tinted background (light/dark paired) — toggle via JS on validation failure, alongside any `.form-error` text |
| `.btn .spinner` | white-tinted variant of the base `.spinner` class, for use inside a button mid-request |
| `.mobile-menu-toggle` | now flex-centered so an inline SVG sits correctly at the `max-width: 768px` breakpoint |
| `#app-version-badge` | injected by `js/app.js` on `DOMContentLoaded` (not a CSS class you add yourself — it's fully automatic on every page that includes `js/app.js`, admin included). Fetches `/api/health`, renders `v<package.json version>` as a small, dim, fixed bottom-right tag. Don't hand-add a version string to any page's HTML — bump the version with `npm run version:patch/minor/major` in `03_backend/` instead, it propagates everywhere on its own. |

**JS helper pattern** (currently duplicated inline per page in `<script>` blocks — copy this pattern rather than reinventing it; a shared `/js/ui-helpers.js` would be the next step if this grows past 2-3 pages):

```js
function setBtnLoading(btn, loading) {
  if (!btn) return;
  if (loading) {
    btn.dataset.originalText = btn.dataset.originalText || btn.innerHTML;
    btn.disabled = true;
    btn.innerHTML = '<span class="spinner"></span>';
  } else {
    btn.disabled = false;
    if (btn.dataset.originalText) btn.innerHTML = btn.dataset.originalText;
  }
}
function setFieldError(id, hasError) {
  const el = document.getElementById(id);
  if (el) el.classList.toggle('has-error', hasError);
}
```
Wrap every async form submit (`await API.post(...)`) with `setBtnLoading(btn, true)` before the call and `setBtnLoading(btn, false)` in a `finally` (or on both success/catch paths if there's a redirect on success that makes `finally` unnecessary).

## 4. Navbar (copy-pasted per page — no shared partial exists)

Every page hand-copies the same navbar markup (confirmed via grep — this is a static Express file server, no templating layer). When touching a page's navbar, bring it to the current pattern:

```html
<a href="/index.html" class="navbar-logo">
  <svg class="icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" aria-hidden="true">
    <rect x="2" y="3" width="20" height="14" rx="2" ry="2"></rect>
    <line x1="8" y1="21" x2="16" y2="21"></line>
    <line x1="12" y1="17" x2="12" y2="21"></line>
  </svg>
  ประกอบ PC <span>Pro</span>
</a>
<button class="mobile-menu-toggle" id="mobile-menu-btn" aria-label="Toggle menu">
  <svg class="icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" aria-hidden="true">
    <line x1="4" y1="6" x2="20" y2="6"></line>
    <line x1="4" y1="12" x2="20" y2="12"></line>
    <line x1="4" y1="18" x2="20" y2="18"></line>
  </svg>
</button>
```
The `mobile-menu-btn` click handler in `app.js` only toggles `classList` on sibling nav elements — it never touches the button's `innerHTML`, so this swap is always safe.

## 5. Verify visually before calling it done

Don't ship a CSS/markup change on a claim alone. Start the backend (`cd 03_backend && npm start` — MySQL connection failing is fine, static file serving still works) and drive it with Playwright (see `run` skill; `chromium-cli` was not available in this environment, fell back to a local Playwright + Chromium install). Minimum bar per page touched:
- Screenshot in light mode
- Screenshot in dark mode (`localStorage.setItem('pcbuilder_theme', 'dark')` then reload)
- `console --errors` / `page.on('console')` check — a page can render its shell while a script silently throws
- Any new interactive element (tab, modal) actually clicked, not just eyeballed in the static markup

## 6. Fix adjacent bugs you notice, don't scope-creep past them

While redesigning `login.html` two real (pre-existing, unrelated-to-styling) bugs were found and fixed because they were one line each and directly adjacent to code being touched: a `getElementById('login-email')` typo (correct id was `login-identifier`) that broke post-reset autofill, and OTP digit-input queries (`document.querySelectorAll('.otp-digit')`) that weren't scoped to their own modal and could read the wrong 6 inputs. Small, contained, directly-adjacent bugs are fine to fix in passing. Don't go hunting for unrelated bugs across the file — that's a separate task.

A bigger example from `profile.html`'s seller KYC form: an interrupted redesign pass left the visible form with 3 fields (`kyc-idcard`, `kyc-bank`, `kyc-phone`) while the submit handler read 6 different ids that didn't exist in the DOM (`kyc-fullname`, `kyc-bankname`, `kyc-bankaccount`, `kyc-bankaccountname`, `kyc-docurl`) — a guaranteed crash on submit, plus the backend's `POST /auth/verify-seller` hard-requires `bank_account` and `kyc_document_url`, neither of which had an input at all. This was too large to be a "one-line" adjacent fix, but shipping a form that crashes on submit is worse than a contained scope increase, so it was rebuilt properly: split the combined bank field to match the backend's distinct `bank_name`/`bank_account`/`bank_account_name` params, and added a real file-upload flow for the KYC document (reusing the existing `POST /api/upload` pattern already used by `sell-product.html`'s photo uploads) rather than leaving a required field with no way to fill it. **Lesson: if an interrupted or partial edit leaves a form's fields and its submit handler out of sync, treat it as a correctness bug to fix fully, not a styling nit to leave alone** — cross-check `getElementById` calls against actual DOM ids (and against what the backend endpoint actually requires) whenever you touch a form, not just the fields that happen to already look re-styled.

## 8. Two more bug classes found during the feature-completion pass (2026-08-12) — check for these specifically

**`${expr}` template-literal syntax only evaluates inside a JS template literal.** A page can have a local `ICONS` object of pre-built SVG strings (the pattern in §3), used correctly inside `<script>` (e.g. `` `<h3>${ICONS.truck} title</h3>` `` inside a function that builds a string). But if that same `${ICONS.x}` syntax gets pasted into **static HTML markup outside `<script>`** (e.g. a `<div id="some-modal">` block sitting directly in the page body), the browser does NOT evaluate it — it renders as literal text `${ICONS.x}`. This happened in `inbox.html`: 4 modals (`#shipped-modal`, `#payment-modal`, `#slip-modal`, `#tracking-detail-modal`) live in raw HTML below the closing `</script>` tag, and got `${ICONS.x}` pasted into them instead of literal `<svg>...</svg>` markup. **Before using `${ICONS.x}` (or any `${...}`) anywhere, confirm the exact byte range is inside a `<script>...</script>` block** — check the file for where `<script>` opens/closes, don't assume based on indentation or nearby code. A quick audit: `grep` for `\$\{` outside `<script>` ranges (see the one-off Node script pattern used this session — build a list of script byte-ranges, then flag any `${...}` match whose index falls outside all of them).

**A helper function being *called* doesn't mean it's *defined*.** `profile.html` called `setBtnLoading`/`setFieldError`/`clearFieldErrors` (the shared page-local pattern from §3) throughout its KYC and seller-settings forms — but the actual `function setBtnLoading(...) {...}` definitions were never pasted into that file's `<script>` block during an earlier edit. This is a silent bug: no syntax error (calling an undefined function is only a *runtime* `ReferenceError`, and only on the exact code path that calls it), so it survives a `node -c` syntax check completely undetected. **Whenever a page uses the `setBtnLoading`/`setFieldError`/`clearFieldErrors` pattern, grep that same file for `function setBtnLoading` (etc.) and confirm it's actually there** — don't assume copying the *call site* from `login.html` means the *definition* came with it.

**A link/redirect to a page that was never built.** Found 2026-08-13 in 3 separate places: `products.html`'s navbar linked to `/builds.html`, and both `js/builder.js`'s `saveBuild()` and `profile.html`'s build-card title linked/redirected to `/build-detail.html?id=...` — **neither file exists anywhere in `04_frontend/`**. Same root cause as the two bugs above: no syntax error, nothing a linter catches, only surfaces when a user actually clicks through (404, or in the redirect case a confusing "stuck on the same page" experience since the browser navigates to a 404 that isn't visually distinct from a slow load). **Before adding any `href`/`window.location.href` to an internal page, `ls 04_frontend/*.html` (or grep the exact filename) and confirm the target file actually exists** — don't assume a page exists just because another page links to it or a variable name implies it (`build.id` existing doesn't mean `build-detail.html` does). When a "detail page" redirect target turns out not to exist and the info is already shown inline elsewhere (as it was here — the build card already shows price/likes/comments/edit/delete), the fix is usually to point at an existing page/tab, not to build the missing page.

## 10. Second hardening pass (2026-08-12) — 🟡-tier fixes + seller review system

Beyond §9, a second pass fixed 5 items flagged as "needs verification before fixing" plus one adjacent bug found along the way, then built the seller review system end-to-end (design approved by the user first — see the review-system row in §9's table):

* `POST /api/upload` now requires auth (`authMiddleware`) — was previously open with no auth check at all.
* `GET /products` N+1 query fixed (`Promise.all` instead of a sequential for-loop over `attachPhotos`) — response shape unchanged, no frontend impact.
* All `500`-level error responses across the 6 controllers now return a generic Thai message instead of raw `error.message` (see `utils/errorHandler.js`) — `400`/`403`/`404`/`409` messages are untouched.
* Login/register/OTP endpoints are now rate-limited (`express-rate-limit`, loose thresholds — 20/15min for auth, 10/15min for OTP — chosen specifically so they don't interfere with live demo/testing).
* **Bank account column bug** (found while investigating, unrelated to the 🟡 list): `registerSeller`/`verifySellerIdentity` wrote the seller's bank account to the legacy `bank_account_number` column, but `bookingController.js` (buyer-facing payment display) reads from `seller_bank_account` — a different column. Newly-registered sellers had no bank account visible to buyers until they separately visited seller-settings. Fixed by writing both columns together going forward, plus a one-time backfill (`seller_bank_account = COALESCE(seller_bank_account, bank_account_number)`) for existing rows — 3 of 4 sellers in the dev DB were affected before the fix.
* **Admin sidebar is now mobile-responsive** (2026-08-12) — off-canvas pattern below 768px (same breakpoint the rest of the site uses), hamburger toggle in `.admin-header`, dark overlay backdrop, auto-closes on tab switch. Purely additive CSS/JS (new `.admin-mobile-toggle`/`.admin-mobile-overlay`/`.mobile-open` rules inside a `@media (max-width: 768px)` block) — desktop layout is byte-for-byte unchanged, verified with side-by-side screenshots.
* **`GET /products` pagination implemented** (2026-08-12) — see [[07_document/API_Documentation]] for the new `{data, total, page, totalPages}` envelope. This was a coordinated change across 4 frontend call sites (`products.html`, two spots in `index.html`, one in `profile.html`) since the response shape changed for everyone, not just the paginated listing page.
  - **Found in the process**: `index.html`'s homepage script was reading `prodRes.products` — a key the backend had never actually returned (it returned a bare array). This meant `products` silently evaluated to `[]` on every homepage load, and the "คอมเซ็ตวางขาย" / "หมวดหมู่ยอดนิยม" / "ร้านค้าแนะนำ" sections had been showing their empty-state messages unconditionally, regardless of how many real listings existed. This predates this session's pagination work — likely a stale expectation left over from an earlier redesign pass that assumed an envelope shape that was never built. Fixed by pointing it at the new `.data` key; verified via Playwright that the homepage now renders real product cards instead of the empty state.
  - `index.html`'s search-autocomplete (`res.length`/`res.slice`) and `profile.html`'s seller-own-listings filter also updated to read `.data`; the seller-listings call was additionally bumped to `limit=100` since it filters client-side across the whole catalog and would otherwise silently miss a seller's own products sitting past page 1.
* **`orders.total_price` changed from `INT` to `DECIMAL(12,2)`** (2026-08-12, done as a separate follow-up after the user asked specifically) — found while investigating the review system: old test orders had `total_price` values that had overflowed to `2147483647` (INT32 max) from the pre-fix string-concatenation bug, which was corrupting the admin dashboard's revenue SUM (was showing ฿4.7 billion). Fixed the bad rows' data first (safe, isolated — recomputed from `order_items`, zero schema/code risk) as its own step, then did the schema change together with the 3 call sites that called `.toLocaleString()` directly on `total_price`-derived values without a `Number()` wrap (`bookingController.js`'s `uploadPaymentSlip`/`exportLegalEvidence`, `adminController.js`'s `getDisputes`) — this is the same "mysql2 returns DECIMAL as string" bug class that recurs throughout this codebase — see [[07_document/Database_Schema]] for the full writeup. Verified with a before/after test proving the exact string-vs-number failure mode.
